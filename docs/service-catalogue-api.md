# Service catalogue back-office API

`/api/v1/backoffice/service-catalogue` is the Core-owned staff contract for service pricing metadata. All authenticated staff may read entries, Ops and audit history. Only Administrators may create, update or delete mutable service entries; the seeded Product entry is read-only for everyone. Both the endpoint policies and the service layer enforce that matrix.

`GET /ops` is the only client source for service, price-method and audit-action numeric values, Russian labels and route aliases. Its currency catalogue contains RUB (`643`) with symbol `₽` and USD (`840`) with symbol `$`; clients use these `symbol` fields for catalogue prices and currency selectors, never derive symbols from aliases. The global `Currency` enum still contains EUR for unrelated exchange-rate and order-limit features. Ops also publishes numeric limits, the `Europe/Moscow` availability timezone and caller capabilities.

Entries support five mutually exclusive shapes. `currency` is required and denotes the resulting charge. `intervalCurrency` is null and `bands` is empty except for Stepped:

Each Ops service publishes `allowedCurrencies` and `allowedPriceMethods` as numeric values from the pricing catalogues; every service permits both RUB/USD and all five methods. Editors consume these lists without service-specific restrictions. Percent uses USD regardless of service, and interval boundaries are always in USD. Product amounts always use the current unit price × quantity; its catalogue definition remains metadata rather than an applied tariff. Domestic delivery (300) and CustomsPayments (800, «Таможенные платежи», `customs-payments`) use ordinary catalogue tariffs, including their method, currency and snapshot.

The specification's current USD/RUB assignments describe how to configure Demo prices, except that Percent always produces USD. Other tariff-driven components use the selected method and charge currency. Percentage uses the USD merchandise base and USD minimum/maximum; results are converted to RUB for aggregation. Stepped boundaries use USD merchandise value; its charge currency remains configurable. Every band must explicitly supply `from`, `by` (including null for the final band), and `amount`.

- Percent (0): `percentage` is greater than zero and at most 100 with four fractional digits; `currency` is USD. Optional nonnegative USD `minimumAmount` and `maximumAmount` cap the resulting charge, not the merchandise base; `amount` is absent.
- Fixed: nonnegative `amount` with two fractional digits and a required RUB or USD `currency`; percent fields are absent.
- Manual: required RUB or USD `currency`; all catalogue amount and percent fields are absent.
- Auto (300): the same definition shape as Manual, but amounts come only from trusted integrations and cannot be supplied by staff. Missing imports stay not calculated.
- Stepped (400): `intervalCurrency` is fixed to USD, independently of charge `currency`, and `bands: [{ from, by, amount }]`. The first `from` is null (no lower bound); later `from` equals the preceding `by`, and the last `by` is null (no upper bound). Numeric bounds and charges are nonnegative two-decimal amounts. Selection uses USD unit price × quantity. Each upper bound is inclusive; a subsequent lower bound is exclusive, so a shared threshold belongs to the preceding band. Exactly one flat charge applies.

`GET /ops` publishes `limits.maximumBands = 100`. Currency, method, interval and nested band validation applies identically to audit snapshots. The fresh schema seeds one immutable Product (`service=0`) definition: ID 1, Manual, USD, no amount and unbounded availability. Its UTC timestamps and UUID version are generated at schema-application time. Product may be read but not created, edited, reclassified, deleted, or replaced, including by an Administrator. Other services retain audited Administrator CRUD; no monetary tariff amounts are seeded.

`availableFrom` and `availableBy` are nullable inclusive Moscow calendar dates. Null `availableFrom` means any earlier date; null `availableBy` means any later date. Both nulls mean all dates. Periods for the same service cannot overlap, including at a shared boundary date. PostgreSQL enforces this with the `ex_service_catalogue_entries_service_period` exclusion constraint; Core performs the same check first for useful field errors and non-relational tests.

`POST /`, `PUT /{id}` and `DELETE /{id}` serialize through one catalogue advisory transaction lock. Update and delete require the opaque current UUID `version`. Every successful mutation stores the entry and an immutable audit event in one transaction using one server-clock snapshot. Create events expose only `after`, updates expose typed `before` and `after`, and deletes expose only `before`; audit remains after the entry is deleted.

`GET /audit` uses the shared paged envelope. Page sizes are 1–100. Filters are numeric `service`, numeric `action`, positive `entryId`, and an actor-name or entry-ID `search` of at most 200 characters. Sorts are `timestamp`, `service`, `action`, or `actor`, with `asc`/`desc`. Invalid filters and mutations use Russian RFC 9457 Problem Details with stable catalogue codes and field mappings.

## Order pricing

Governed by PRICE at `sara-fan/sarafan@981eb0fce77d92fde28e3270cc761e69c5925c48`; FR-PRICE-042 is deferred. The latest valid stored official USD/RUB is used without spread; nominal is respected and EUR is not required for pricing. Existing EUR merchandise-limit validation remains independent.

- `GET /api/v1/backoffice/orders/pricing/ops`: catalogue metadata, component states, 24-hour validity and caller `canManage`.
- `GET /api/v1/backoffice/orders/{orderNumber}/pricing`: current typed calculation, current order `updatedAt`, edit/confirm capabilities, current active tariff definitions, confirmation validity/expiry and the latest 100 immutable history entries. All staff may read.
- `PUT .../{orderNumber}/pricing`: Administrator/Shift manager only; `{ expectedUpdatedAt, inputs: { manualAmounts, selectedServices } }`. Manual amount keys are numeric ServiceKind values and must have an active Manual tariff. Selected services may contain photo, inspection and insurance only. Auto and fixed values cannot be overridden. This saves and recalculates a forecast, not a manually supplied total.
- `POST .../{orderNumber}/pricing/confirm`: `{ expectedUpdatedAt }`, same roles. Requires a saved complete calculation and UnderReview status. Freezes that saved calculation and changes status to QuoteReady atomically. Further mutations are rejected, including after expiry; expired financial values remain readable. Requote/checkout/payment workflows are not introduced here.

`manualAmounts` uses JSON object keys containing the invariant decimal ServiceKind value, for example `{"100":3.25}`, in requests, responses, history and newly stored snapshots. Core can still read earlier snapshots whose keys contain enum identifiers, but always emits numeric keys; existing historical payloads are not rewritten. Other enum fields retain their numeric JSON representation.

Creation records a forecast. Changes to merchandise price or quantity append a recalculated forecast; unrelated product corrections preserve the financial result. Every component retains original currency and a separately rounded RUB amount. Half-up rounding to two decimals is applied to components before summation. Calculated zero is distinct from missing and not applicable. Percent components use USD; other tariff-driven components use their configured RUB/USD charge currency and method. The separate product input remains USD. Catalogue Ops publishes read-only `includedInTotal`, calculated by `ServiceKind.IsIncludedInTotal()`: false for domestic delivery and customs payments, true for all other services. Only included applicable components contribute to the total and its availability; unknown excluded components do not block confirmation. Back Office places included components above «Итого» and excluded components below it, using Ops names. Manual values for both services use `manualAmounts` (keys `"300"` and `"800"`); neither service is optional. Their tariffs are configured by the administrator, not seeded.

`IAutomaticPriceSource` is the trusted integration seam for Auto service amounts. No external provider is invented or configured: without an implementation, those components are explicitly not calculated. Merchandise itself uses the current reviewed product. No manual FX endpoint or customer UI is introduced. Migration `0_3_0_ServiceCatalog2` removes the service-kind check constraint so adding service kinds does not require database migrations; the flag needs no database column. Ship Core and Back Office together. The old separate-input request/snapshot format is unsupported; no compatibility adapter or data backfill is provided.
